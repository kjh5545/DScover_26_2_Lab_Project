## 1. 작업 정리 — 질문 생성 프롬프트 v2.2~v2.3.3 개선 및 검토

**최종 상태: v2.3.3을 팀 검토 후보로 정리함. S008·S005의 공유된 출력에서 개선과 잔여 한계를 확인했으며, 일반화 검증 완료나 코드 반영 완료를 뜻하지 않음.** 아래는 오늘의 변경·실험 기록이다. 앞선 v0~v2.1 기록은 당시 이력으로 보존한다.

### 결정한 설계 원칙

- 사용자는 환자이며, 환자가 직접 답하거나 기존 기록을 제공할 수 있는지를 함께 고려한다. 그 안에서 **판정 영향 → 공통성 → 시험별 균형** 순으로 정한다.
- 중요도 원칙은 사람이 정하고 AI가 입력 기준에 적용한다. 검증된 임상 중요도 점수나 의학적 우선순위 체계를 만든 것은 아니다.
- ‘시험별 균형’은 비슷한 중요도의 질문 중 한 시험에만 몰리지 않도록 고르는 보조 기준이다. 시험마다 같은 개수를 할당하거나 더 중요한 질문을 밀어내는 뜻이 아니다.
- 선정 기준을 제외 기준보다 항상 먼저 묻거나, 그 반대로 일괄 정하지 않는다. 기준 수가 많다는 이유만으로 우선순위가 자동 결정되지 않는다.
- 검사 시행 여부와 그 결과지 보유 여부, 같은 약의 용량·기간, 흡연량·흡연 기간은 같은 주제로 묶을 수 있다. 여러 약을 포함한 목록을 한 번 요청하는 것도 가능하다. 서로 다른 약의 상세 질문은 나눈다.
- 두통 일수와 전조 횟수, 진단 결과와 치료·수술 계획, 임신·수유와 피임 방법·시작 시점은 나눈다. 임신·수유는 함께 묻되 어느 상태인지 구분한다.
- 혈뇨·두통·방광내시경처럼 익숙한 용어는 간결하게 쓴다. 낯선 질환명은 정확한 이름을 유지하고 짧은 풀이를 붙인다.
- 원문의 기간·기준일·횟수·용량·약물명·투여 경로·예외 범위를 바꾸지 않는다. 월별 조건을 평균·합계로 대체하지 않는다.
- 기록이 필요하거나 민감한 질문이라는 이유만으로 생략하거나 자동 후순위로 두지 않는다.
- 이미 답한 내용은 다시 묻지 않는다. 같은 기준에 필요한 다른 정보가 남았다면 그 부분만 후속 질문이 가능하다. 모른다는 답변에는 기록 확인을 대안으로 제시할 수 있으나, 기록도 없다고 답했다면 같은 요청을 반복하지 않는다.

### 실험 조건과 해석 범위

- 사용자가 웹 채팅에서 실행하고 답변을 공유했으며, 이 기록은 그 출력에 대한 정성 검토다.
- 사용 모델은 사용자가 “Claude Opus 4.8”이라고 알려 준 명칭으로 기록한다. 서비스의 실제 모델 표시는 별도로 확인하지 않았다.
- S008은 후보 시험 2개·모름 기준 23개, S005는 후보 시험 2개·모름 기준 24개를 사용한 비교 기록이다.
- 모든 최신 실험의 질문 수는 5개. JSON은 코드에서 읽기 위한 형식이며, review는 실험 검토용 추가 정보다. 실제 코드의 지원 필드로 확정하거나 HANDOFF 형식을 변경한 것은 아니다.
- 반복 실행·독립 채점·다른 모델 비교·실제 환자 답변을 받은 재평가 실험은 수행하지 않았다.
- v2.3.3 부분 수정안 이후 한 차례 다시 공유된 출력은 앞선 v2.3.2 결과와 동일했다. 독립적인 새 실행으로 세지 않는다. 이후 전체 v2.3.3 프롬프트를 받고 공유한 다른 출력이 아래 최종 검토 대상이다.
- 비교용 S005 입력의 I7·I8 같은 참여 의향 항목은 최신 ‘등록 후 확인’ 정책과 정합성을 별도 확인해야 한다. 오늘은 정답 레이블을 변경하지 않았다.

### v2.3.3 규칙 요약 — 실행 원문을 대신하는 전문이 아닌 검토용 정리

1. 질문 수는 입력에서 받는다. 환자의 답변·기록 제공 가능성을 고려하며 판정 영향, 공통성, 시험별 균형 순으로 우선순위를 설명한다.
2. 표현이 달라도 같은 사실을 묻는 기준은 의미로 묶는다. 같은 기준이라는 이유만으로 서로 다른 사실을 억지로 묶지 않는다.
3. 한 질문에 한 주제, 최대 두 문장. 같은 사실의 후속 확인은 허용하되 별개 측정값·진단과 계획 등은 분리한다.
4. 익숙한 용어는 간결하게, 낯선 용어는 원래 명칭과 짧은 풀이를 함께 쓴다.
5. 검사 수치를 기억으로 답하게 하지 않는다. 검사·기록의 존재와 실제 기준 충족 여부를 구분한다.
6. 특정 진단이 필요한 기준은 그 진단명을 유지한다. 증상만으로 진단 사실을 전제하지 않는다.
7. 적격·부적격이나 기준 확인 완료를 환자에게 단정하지 않는다.
8. 민감한 질문은 부드럽게 묻되, 독립 질문이라는 이유로 밀어내지 않는다.
9. 입력에서 지정된 질문 후보만 사용하고, 보류한 기준과 이유를 빠짐없이 남긴다. 기록 요청이 가능한 항목을 의료진 판단 영역이라는 이유만으로 제외하지 않는다.
10. 원문 조건을 보존한다. 등록일이 없으면 오늘을 등록일로 대신하지 않고 실제 날짜·연월·투약 시작일과 중단일을 수집하여 나중에 대조한다. 원문이 모호하면 해석 필요 사항으로 남긴다.
11. resolves는 관련 기준 연결이며 판정 완료 표시가 아니다. asked_info는 실제 질문에 있는 정보, remaining_info는 아직 묻지 않았거나 기록 검토가 필요한 정보만 적는다.
12. 질문의 대상·신체 부위·검사·치료를 입력에 맞게 명확히 쓴다.
13. 기존 답변을 재사용한다. 후속 질문은 아직 확인되지 않은 정보만 묻고, 이미 없다고 한 기록을 반복 요청하지 않는다.

출력 구성: questions(question, needed_info, resolves), not_asked(trial, criterion_id, reason), review(priority_notes, criterion_checks). JSON의 문자열·키에는 일반 큰따옴표를 사용한다.

### 보류된 기준

- NCT07348783: I6, I7, I8, E1, E2, E3, E4, E5.
- NCT04063540: I4, I6, E1, E2, E4, E5, E10.
- 출력의 not_asked 사유는 모두 ‘질문 수 제한으로 보류’.
- 고유 관련 기준 9개 + 보류 15개 = 입력 기준 24개. 이는 기준 ID가 빠지지 않았다는 뜻이며, 관련 기준 9개가 모두 해결되었다는 뜻은 아니다.
- 두 시험에 동시에 연결된 질문은 이번 출력에서 0개. v2.3.2의 진단 질문은 두 시험에 연결되었으므로, 의미에 따른 묶기의 일관성은 추가 검토가 필요하다.

### 이번 출력에서 개선된 점

- 조짐 횟수를 월평균으로 합치지 않고 각 달의 횟수와 연·월을 요청함.
- 등록일 미상 상태를 review에 남기고, ‘등록 전 3개월’ 해당 여부를 나중에 대조하도록 함.
- 약물 사용 시작·중단 날짜와 경구·주사·주입 치료를 포함한 기록을 요청함.
- 기록 제공 가능 여부만으로 투약 조건 충족을 확정하지 않음.
- 약물 병용 예외를 임의로 확대하는 표현을 줄이고 원문 범위 보존 필요를 남김.
- 임신·수유를 독립 질문으로 포함하고 각 상태를 구분하도록 함.
- 우선순위 설명에서 ‘기록이 필요하므로 후순위’라는 일괄 원칙을 사용하지 않음.

### 남은 문제 — 전면 통과로 기록하지 않음

- **Q2와 asked_info 불일치:** 질문은 ‘만성 편두통’을 묻는데 I3의 asked_info에는 ‘만성/고빈도 편두통’이 들어 있다. 실제로 묻지 않은 고빈도 진단까지 확인한 것처럼 적지 않아야 한다.
- **Q2의 진단 범위:** 입력 I1의 cluster headache와 I4의 chronic cluster headache를 구분해야 한다. 질문을 ‘만성 군발두통’으로 한정하면 일반 군발두통 진단 여부를 충분히 묻지 못할 수 있다.
- **Q3 수집 기간:** ‘최근 몇 달’은 범위가 모호하다. 연·월과 일지를 요청하고 등록일 미상 한계를 남긴 점은 개선이나, 실제로 목표 3개월 자료를 확보했다고 볼 수 없다.
- **공통 진단 질문 묶기:** 같은 두통 진단 기록을 Q1·Q2에서 각각 요청한다. 의미 묶기의 효율과 한 질문의 답변 부담을 함께 검토할 필요가 있다. 공통 질문 0개 자체만으로 오류라고 단정하지는 않는다.
- 두통 일수·편두통 일수, 만성 군발두통의 관해 기간, 약물·기록의 실제 내용 등은 여전히 미확인이다.
- remaining_info에는 ‘앞으로 필요한 사실’을 기록하고, ‘사전에 가정하지 않는다’ 같은 작성 원칙과 구분할 필요가 있다.

**결론: 목표로 한 일부 오류는 개선되었으나, 모든 규칙을 충족했다거나 다른 환자에서도 안정적이라고 검증한 결과는 아니다. v2.3.3은 잔여 한계를 명시한 팀 검토 후보로 둔다.**

## 3. 역할 범위와 해준·주희 인계 사항

### 현재 작업한 부분

- 5번 질문 생성 프롬프트의 원칙·표현·묶기·우선순위·중복 방지 설계.
- 공유된 결과를 기준에 따라 검토하고, 버전 변경 이유와 한계를 기록.
- 후속 질문에서도 같은 원칙을 적용하도록 설계하는 것은 5번 범위에 포함된다. 다만 후속 질문 실험 전체나 반복 루프 구현을 혼자 추가로 완료해야 한다는 뜻은 아니다.

### 함께 확인할 부분

- 해준: 코드 연결·질문 선택·반복 라운드 제어. 주희: 답변 반영과 6번 재평가·판정.
- 오늘 논의한 코드 정책과 프롬프트 원칙의 정합성 확인: 여러 시험 공통 질문을 무조건 먼저 배치하면 ‘판정 영향 우선’과 충돌할 수 있음.
- 이미 질문한 기준 ID 전체를 이후 후보에서 제외하면, 같은 기준의 남은 정보만 재질문하는 원칙을 구현하기 어려움.
- resolves를 기준 해결 완료로 사용하지 않도록 확인. review의 실험용 필드를 실제 코드에서 받을지 별도 합의.
- 오늘 작성한 v2.3.3을 저장소·실행 코드에 병합했다고 기록하지 않는다. 새 후보의 코드 반영 및 통합 검증은 별도 작업이다.
- 기존 데이터 형식을 바꾸려면 팀 공통 규칙에 따라 먼저 공유한다.

> **10/22 반영 기록 (주희 추가)**: 위 두 정책 충돌은 코드에서 고쳤어요 (질문 순서는 AI가 정한 대로, 답을 받았는데도 모름인 기준은 한 번 더). review는 실험용 전문(`QUESTION_SYSTEM_PROMPT_REVIEW`)에만 남기고, 질문 루프는 review 출력을 뺀 버전을 써요. 코드 반영과 통합 검증(Sonnet 5.5): 질문 루프 5/20 → 18/20 (v2.1 17/20).

## 4. 최종 검토 보충

- S005의 두통 일수와 전조 횟수는 서로 다른 측정값이므로 분리하기로 결정함. 최종 v2.3.3에서는 두통 일수 질문이 선택되지 않아 두 항목의 실제 분리 생성까지 검증한 것은 아님.
- 후속 질문 원칙은 ‘이미 받은 동일 정보는 재질문하지 않고 같은 기준의 미확인 정보만 추가 질문’으로 정함. 코드 적용 방식은 팀과 조율이 필요하며, 기존 답변이 있는 후속 라운드 실험은 이번에 수행하지 않음.
- S008은 v2.2·v2.2.1, S005는 v2.3.1~v2.3.3 출력을 검토함. 최종 v2.3.3을 두 케이스 모두에 재적용한 검증은 아님.

## 부록 A. 실제 실행한 v2.3.3 프롬프트 전문
